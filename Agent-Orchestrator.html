The Agent Orchestrator — how 9 AI agents are actually run

Having 9 AI agents is easy. Making them run in the right order, some at the same time, looping back when something is unsafe, saving progress after every step, and running exactly once even when the browser asks 20 times — that is the orchestrator. This document explains every part of it in very simple words.

⚙️ 100% custom TypeScript ⚡ Parallel fan-out 🔁 Verify-and-loop cycle 🔒 Atomic run-once claim 💾 Crash-safe state ☁️ Serverless-proof

The short version: lib/agents/pipeline.ts is the orchestrator. It is a plain TypeScript file — no framework — that calls the 9 agent functions in a planned order, runs independent ones together, feeds safety complaints back into the prescriber, and writes every result to MongoDB the moment it appears.

Basics

1 · What is an orchestrator? (start here)

Imagine a kitchen in a restaurant. You have 9 cooks, each expert at one thing: one chops, one fries, one plates, one tastes for salt, one checks for allergies.

Now — who tells them when to work? Who makes sure the chopping happens before the frying? Who lets the salad cook and the soup cook work at the same time because they don't depend on each other? Who sends the dish back to be re-cooked if the taster says it's too salty?

That person is the head chef. In software, that is the orchestrator.

The orchestrator's exact job in MediIQ

  • Order — decide which agent runs when.
  • Parallelism — run independent agents at the same time to save time.
  • Data passing — take Agent 3's output and hand it to Agent 6 as input.
  • Looping — if the safety agents complain, send the work back to be redone.
  • State — remember what has finished, so a page refresh doesn't lose it.
  • Errors — decide what happens when an agent fails (skip? stop? continue?).
  • Once-only — make sure the whole thing doesn't accidentally run twice.
The single most important sentenceThe agents are the intelligence. The orchestrator is the plumbing and the rules. Most of the hard engineering in a multi-agent system is in the plumbing, not the prompts.

2 · This is custom-built — not LangGraph

There are ready-made frameworks for running AI agents: LangGraph, LangChain, CrewAI, AutoGen. MediIQ uses none of them.

Proof — the only imports in pipeline.ts

import { runAllergyAgent }         from "./agent8";

Why build it by hand?

🎯 The flow was simple enough

A fan-out, a straight line, and one loop. A whole graph framework would be heavy machinery for that shape.

💾 Full control of persistence

Each agent's result must land in a specific MongoDB field, in a specific way (dot-notation) so nothing gets overwritten. Frameworks abstract that away.

☁️ Serverless timing problems

Vercel kills background work the instant a response is sent. Solving that needed direct control over what is awaited and when.

📦 Fewer dependencies

No extra library to version-bump, break, or debug through. The whole orchestrator is one readable file.

How to say this in an interview"I wrote the orchestration myself. It's a 9-agent pipeline with a verify-and-loop cycle, parallel fan-out, and an atomic once-only claim so it's safe under polling and serverless. I considered LangGraph — it gives you graph state and cycles out of the box — but my flow was mostly linear with one conditional loop, and I wanted direct control over persistence and the serverless timing, so a framework would have been overhead."

That shows a decision, not ignorance. That is what is actually being tested.

Building Blocks

4 · The agent contract — the key idea ⭐

Before orchestrating anything, every agent had to look the same from the outside. This is called a contract or interface: a rule that says "no matter what you do inside, you must accept input like this and return output like this."

lib/agents/types.ts — every agent obeys this
export type AgentFn<TInput, TOutput> = (
  input: TInput,
  onPartial?: (partialText: string) => void,   // optional live streaming
) => Promise<AgentResult<TOutput>>;

export interface AgentResult<T> {
  agentId:     number;      // 1–9
  agentName:   string;      // "Similar Cases Agent"
  status:      "ok" | "flag" | "error";
  input:       unknown;     // what it was given (for debugging)
  output:      T | null;    // the actual result
  feedsInto:   number[];    // which agents use this result
  triggeredBy: number[];    // which agents caused this one to run
  logs:        string[];    // human-readable trace of what it did
  durationMs:  number;      // how long it took
  error?:      string;      // why it failed, if it did
}

Why this one idea makes everything else possible

🔌 Swappable

Every agent is a black box with the same plug shape. The orchestrator calls all 9 the same way, without knowing what's inside.

🚦 Three-state status

Not just success/fail. flag means "I worked, but I found a problem" — that is what powers the safety loop.

🔍 Self-documenting

logs and durationMs come back from every agent, so the admin dev tools can show exactly what happened and how slow it was.

🕸️ Self-describing graph

feedsInto / triggeredBy mean each result carries its own place in the pipeline.

The 3 statuses in plain words ok = worked fine.
flag = worked, but something needs attention (e.g. Agent 7 found a dangerous drug, or Agent 2 found a medicine name it couldn't recognise).
error = could not do the job at all.

This is exactly what a framework would give you — a uniform node interface. Writing it yourself in 15 lines is a good demonstration that you understand why frameworks have it.

7 · The model-routing layer

Agents don't talk to an AI model directly. They call helpers in llm.ts, which decides which model answers. This is orchestration too — orchestrating models instead of agents.

The central dispatch (llm.ts)
async function dispatch(prompt, mode, { task, onChunk, timeoutMs = 60_000 }) {

  if (mode === "gemini_only")   return callGemini(prompt);
  if (mode === "deepseek_only") return callDeepSeek(prompt);

  // MIXED modes: Gemini is reserved for the prescriber ONLY
  const other = mode === "gemini_ollama_race" ? "ollama" : "deepseek";

  if (task === "prescription") {
    return runPreferGemini(prompt, other, { onChunk, timeoutMs });  // ← the race
  }

  return callOther(prompt, other);   // every other agent uses the cheaper model
}

The "prefer Gemini" race — a neat trick

For the most important step (writing the prescription), both models are asked at the same time:

1
Fire both immediately

Gemini and the backup model start working in parallel the moment the prescriber begins.

2
Race Gemini against a 60-second timer

Promise.race([geminiPromise, timeoutPromise]) — whichever finishes first wins.

3
If Gemini answers in time → use it

Preferred, because it's the strongest medical reasoner.

4
If Gemini is slow or fails → use the other

Its answer is already nearly ready, because it never stopped working. That's what saves the wall-clock time — no waiting 60s and only then starting the backup.

5
If both fail → throw a clear error

Naming both failures, so debugging is easy.

Why this design is smartA naive fallback is sequential: try Gemini, wait 60s, fail, then start the backup — total 60s + backup time. This runs them concurrently, so the worst case is roughly max(60s, backup time), not the sum. Same reliability, much faster. It also records geminiError so the UI can show "⚠ Gemini failed → DeepSeek" honestly.
How It Runs

8 · The two entry points (and the serverless problem)

The orchestrator does not run continuously. It is started twice, by two API routes:

RouteStarted whenRuns
POST /api/appointments/[id]/run-precallPatient presses "Lock details"Agents 3, 4, 5 (in parallel)
POST /api/appointments/[id]/run-pipelineDoctor's post-call page loadsrunPostCallPipeline() — agents 2, 6, 7, 8, 9

⚠️ The serverless problem — a real bug that shaped the design

The natural way to write this is: "reply to the browser instantly, and let the AI keep working in the background." On a normal always-on server that works fine.

On Vercel it does NOT workVercel runs code in serverless functions. A serverless function is frozen the moment it sends its response. So any background task started with setImmediate() or a floating promise is killed instantly — the pipeline would silently never run, and the doctor's page would poll forever showing "Waiting".

The fix

Before (broken on Vercel) vs After (correct)
// ❌ BEFORE — end-call route
appt.agentPipelineStep = "call_ended";
await appt.save();
setImmediate(() => runPostCallPipeline(id, transcript));  // KILLED on Vercel
return NextResponse.json({ ok: true });                   // ← freeze happens here

// ✅ AFTER — dedicated run-pipeline route
export const maxDuration = 300;          // ask Vercel for up to 300 seconds

await runPostCallPipeline(id, appt.transcript ?? "");   // ← AWAITED
return NextResponse.json({ ok: true, step: done });     // reply only when finished

The route now waits for the whole pipeline, so the function stays alive. maxDuration = 300 asks the platform for a longer time limit (Vercel Pro allows up to 300s; the free Hobby tier caps at 60s).

This is a great interview storyIt shows you hit a real platform constraint, diagnosed why (function freezing), and redesigned around it — rather than just "it didn't work so I retried". Frameworks like LangGraph do not solve this for you either; it's a deployment-model issue.
How It Runs

9 · Running exactly once — the atomic claim ⭐

The problem

The doctor's page polls every 2.5 seconds to update the progress bar. If each poll triggered the pipeline, you would get many copies running at once: wasted money, corrupted data, duplicate prescriptions. Worse, the doctor might open two browser tabs.

The solution: claim the job in the database

Before doing any work, the route tries to atomically flip a flag in MongoDB. "Atomic" means the read and the write happen as one indivisible operation — no two requests can both succeed.

run-pipeline/route.ts — the claim
const PRE_AGENT2 = ["idle", "agent_1_done", "agents_345_running",
                    "agents_345_processing", "agents_345_done",
                    "agents_345_failed", "call_ended"];

const claimed = await Appointment.findOneAndUpdate(
  { _id: id, agentPipelineStep: { $in: PRE_AGENT2 } },   // ONLY if not started
  { $set: { agentPipelineStep: "agent_2_running" } },    // mark it started
).select("_id").lean();

if (!claimed) {
  return NextResponse.json({ ok: true, alreadyRunning: true });  // someone else won
}

await runPostCallPipeline(id, appt.transcript ?? "");   // we won — do the work

Why findOneAndUpdate and not read-then-write?

The race condition it prevents
❌ NAIVE (two steps — unsafe):
   Request A: read step  → "call_ended"   ✓ not started
   Request B: read step  → "call_ended"   ✓ not started   ← both think they won!
   Request A: write "running"
   Request B: write "running"
   → PIPELINE RUNS TWICE

✅ ATOMIC (one step — safe):
   Request A: findOneAndUpdate(step is call_ended → set running)  → got a document
   Request B: findOneAndUpdate(step is call_ended → set running)  → got NULL
                                (because A already changed it)
   → PIPELINE RUNS ONCE
The name for this patternIt is a compare-and-swap (or "optimistic lock"). The database itself guarantees only one writer wins, so no extra lock service (like Redis) is needed. Poll all you like — the pipeline still runs once.

The same trick guards the pre-call route, claiming agents_345_running → agents_345_processing.

10 · The state machine — one field runs everything

The orchestrator's entire memory lives in one MongoDB field: agentPipelineStep. It is a simple string that always says where the pipeline currently is.

The full list of states, in order
idle
  ↓
agent_1_done              ← patient summary ready
  ↓
agents_345_running        ← lock pressed, pre-warm claimed
agents_345_processing     ← run-precall is actively working
agents_345_done           ← similar cases + context + allergies ready
  ↓
call_ended                ← video call finished, transcript saved
  ↓
agent_2_running  →  agent_2_done          ← transcription
agent_6_running  →  agent_6_done          ← prescription drafted
agent_7_running  →  agent_7_done          ← drug interactions checked
agent_8_running  →  agent_8_done          ← allergies checked
  ↓   (if flagged, the loop repeats with a "loop_2_" prefix)
loop_2_agent_6_running → loop_2_agent_6_done
loop_2_agent_7_running → loop_2_agent_7_done
  ↓
pipeline_done                             ← finished ✅
pipeline_failed                           ← something went badly wrong ❌

Why a single string is enough (and clever)

🔄 Survives everything

Server restart, page refresh, closed laptop — the state is in the database, not in memory. Reopen the page and it resumes exactly where it was.

👀 Drives the UI free

The doctor's progress bar simply reads this string and finds it in a list. No separate progress system needed.

🔒 Enables the claim

Because the state is a single field, it can be compare-and-swapped atomically (§9).

🐛 Instantly debuggable

One look at the field tells you exactly where a stuck pipeline stopped.

A subtle bug this caused — worth tellingThe slow pre-call agents once finished after the call had ended, and their "I'm done" write reset the state from call_ended back to agents_345_done — so the post-call pipeline never triggered and the page hung forever. The fix was to make that write conditional: only advance the step if it is still in the pre-call state.
The conditional advance (run-precall/route.ts)
// Only move forward if we are STILL in pre-call.
// Never overwrite "call_ended" or any post-call step.
await Appointment.findOneAndUpdate(
  { _id: id, agentPipelineStep: "agents_345_processing" },   // ← the guard
  { $set: { agentPipelineStep: "agents_345_done" } },
);

11 · Phase 1 — parallel fan-out

Agents 3, 4 and 5 do not need each other. Agent 3 searches past cases, Agent 4 fetches medical knowledge, Agent 5 expands allergies. None uses another's output.

So running them one after another would waste time. Instead they are fanned out — started together.

run-precall/route.ts — parallel fan-out
const [s3, s4, s5] = await Promise.allSettled([
  runSimilarCasesAgent({ symptoms, duration, severity, patientAge, patientConditions }),
  runMedicalContextAgent({ patientId, knownConditions, bookingSymptoms }),
  runAllergyContextAgent({ knownAllergies, consultationMentions, suspectedFromFeedback }),
]);

Why allSettled and not all? (important)

The difference, in plain terms
Promise.all      → if ANY ONE fails, the whole thing throws.
                   The two that SUCCEEDED are thrown away. 💥

Promise.allSettled → waits for all three no matter what, and tells you
                     individually: fulfilled or rejected. Nothing is lost. ✅

This mattered in practice: Agent 4 calls external government APIs that sometimes time out. With Promise.all, one slow API would have discarded Agent 3's and Agent 5's completed work — and the pipeline would have marked everything failed.

Unpacking the settled results safely
const a3 = s3.status === "fulfilled" ? s3.value : null;
const a4 = s4.status === "fulfilled" ? s4.value : null;
const a5 = s5.status === "fulfilled" ? s5.value : null;

if (s3.status === "rejected") console.error("[run-precall] agent3 threw:", s3.reason);
// …each failure is logged individually, then each result is saved on its own
Speed winIf the three agents take 25s, 67s and 12s, running them in sequence takes 104 seconds. Running them in parallel takes 67 seconds — the time of the slowest one. And because this happens during the video call, the results are usually ready before the call even ends, so the patient waits ~0s for them.

12 · Phase 2 — the sequential chain

After the call, the remaining agents must run in order, because each one needs the previous one's output. This is a dependency chain.

Why these can't be parallel
Agent 2 (transcript)
   ↓ needs the transcript to exist
Agent 6 (prescribe)      ← needs 2, 3, 4, 5
   ↓ needs a prescription to check
Agent 7 (drug check)  +  Agent 8 (allergy check)   ← both need Agent 6's output
   ↓
Agent 9 (findings)       ← needs the final prescription

The self-healing step (defensive orchestration)

What if the call was very short and the pre-warm (agents 3/4/5) hadn't finished? Agent 6 would get empty context and write a poor prescription. So before prescribing, the orchestrator checks and repairs:

pipeline.ts — ensure pre-call agents exist
if (!agentOutputs.agent3 || !agentOutputs.agent4 || !agentOutputs.agent5) {

  // 1. Re-read the DB first — the pre-warm may have JUST finished
  const fresh = await Appointment.findById(appointmentId).select("agentOutputs").lean();
  for (const k of ["agent3", "agent4", "agent5"]) {
    if (fresh?.agentOutputs?.[k] != null && agentOutputs[k] == null)
      agentOutputs[k] = fresh.agentOutputs[k];      // adopt the finished work
  }

  // 2. Run ONLY the ones still genuinely missing — never redo completed work
  const need3 = agentOutputs.agent3 == null;
  const need4 = agentOutputs.agent4 == null;
  const need5 = agentOutputs.agent5 == null;

  if (need3 || need4 || need5) {
    const [r3, r4, r5] = await Promise.allSettled([
      need3 ? runSimilarCasesAgent(...)   : Promise.resolve(null),
      need4 ? runMedicalContextAgent(...) : Promise.resolve(null),
      need5 ? runAllergyContextAgent(...) : Promise.resolve(null),
    ]);
    // …save only what was newly computed
  }
}
Three good ideas in one block(1) Re-read before acting — the world may have changed since the function started. (2) Do the minimum — only run what is actually missing, never repeat expensive API work. (3) Still parallel + allSettled — the repair itself follows the same safe pattern.

13 · The verify-and-loop cycle ⭐⭐

This is the most interesting part of the orchestrator, and the part interviewers ask about most. It is the thing that makes this a graph with a cycle, not just a straight line.

In plain English

The prescriber writes a prescription. Two checker agents inspect it. If they find a problem, the problem is written down and handed back to the prescriber, who writes a new prescription knowing exactly what to avoid. This repeats at most twice, then it goes to the human doctor.

The actual code

pipeline.ts — the whole cycle
const MAX_LOOPS = 2;
const allFlagged = [];        // problems found, carried between rounds

for (let loop = 0; loop < MAX_LOOPS; loop++) {

  const stepPrefix = loop > 0 ? `loop_${loop + 1}_` : "";   // for the UI

  // ── AGENT 6: prescribe ───────────────────────────────────────────
  await updateStep(appointmentId, `${stepPrefix}agent_6_running`);

  const a6Result = await runReasoningAgent(
    loop === 0
      ? agent6Input                       // first round: plain input
      : { ...agent6Input,                 // later rounds: input + the complaints
          loopContext: {
            loopNumber:   loop + 1,
            flaggedDrugs: allFlagged.map(f => ({
              drug: f.drug, reason: f.reason, flaggedBy: f.flaggedBy,
            })),
          },
        },
  );
  currentPrescription  = a6Result.output;
  agentOutputs.agent6  = currentPrescription;
  await updateStep(appointmentId, `${stepPrefix}agent_6_done`, { agentOutputs });

  if (!currentPrescription?.prescription) break;    // nothing to check — bail out

  // ── AGENT 7: drug interactions ───────────────────────────────────
  const a7Result = await runDrugMedicAgent(a7Input);
  a7Output = a7Result.output;
  await updateStep(appointmentId, `${stepPrefix}agent_7_done`, { agentOutputs });

  // ── AGENT 8: allergy safety ──────────────────────────────────────
  const a8Result = await runAllergyAgent(a8Input);
  a8Output = a8Result.output;
  await updateStep(appointmentId, `${stepPrefix}agent_8_done`, { agentOutputs });

  // ── EXIT CONDITION ───────────────────────────────────────────────
  if (a7Output?.status === "PASS" && a8Output?.status === "PASS") {
    console.log("✅ Agents 7+8 PASS — pipeline complete");
    break;                              // ← the loop ends here
  }

  // ── COLLECT THE COMPLAINTS for the next round ────────────────────
  allFlagged.length = 0;                          // clear old flags first
  for (const v of (a7Output?.perMedicine ?? []))
    if (v.verdict === "FLAG" && v.flagReason)
      allFlagged.push({ drug: v.drug, reason: v.flagReason, flaggedBy: "agent7" });

  for (const c of (a8Output?.checks ?? []))
    if (c.verdict !== "PASS" && c.violates)
      allFlagged.push({ drug: c.drug,
                       reason: `Allergy violation: ${c.violates}`,
                       flaggedBy: "agent8" });
}

The three things that make it a real loop

1️⃣ Feedback

The flags are not just logged — they are injected into the next call as loopContext. That is what makes Agent 6 behave differently the second time. Without this it would just repeat the same mistake.

2️⃣ Exit condition

if (both PASS) break. The loop ends as soon as the prescription is safe — it does not always run twice.

3️⃣ Bounded

MAX_LOOPS = 2. Without a cap, a stubborn model could loop forever, burning money and never finishing.

A worked example

Patient: severe penicillin allergy
ROUND 1 (loop = 0)
  Agent 6 → prescribes Amoxicillin 500mg + Paracetamol
  Agent 7 → PASS (no dangerous drug-drug interaction)
  Agent 8 → FLAG! Amoxicillin is in the penicillin class (HARD_BLOCK)
  Both PASS?  No → collect flags:
      allFlagged = [{ drug: "Amoxicillin",
                      reason: "Allergy violation: Penicillin allergy (confirmed, severe)",
                      flaggedBy: "agent8" }]
  → loop continues

ROUND 2 (loop = 1)     step becomes "loop_2_agent_6_running"
  Agent 6 → sees loopContext with the Amoxicillin complaint
          → prescribes Azithromycin 500mg + Paracetamol instead
  Agent 7 → PASS
  Agent 8 → PASS
  Both PASS?  YES → break ✅

FINAL: Azithromycin sent. Amoxicillin recorded in flaggedDrugs and
       NEVER included in the prescription sent to the patient.

What happens if it still fails after 2 rounds?

Escalation, not infinite retry
if (loop < MAX_LOOPS - 1) {
  console.log(`⚠ ${allFlagged.length} flag(s) — looping back to Agent 6`);
} else {
  console.log(`⚠ Max loops reached — ${allFlagged.length} unresolved flag(s),
               escalating to doctor`);
}

The unresolved flags are saved to flaggedDrugs and shown to the doctor in a red "Rejected Drugs" panel with the reason. The flagged medicines are filtered out before sending, so an unsafe drug can never reach the patient even if the AI kept suggesting it.

The single best line to say in an interview"I bounded the loop and made the fallback a human, not an infinite retry."

That is a safety-engineering answer. It shows you thought about what happens when the AI doesn't converge — which is exactly the failure mode that matters in medical software.

Why two separate checkers instead of letting Agent 6 check itself?

Because a model reviewing its own work is biased toward approving it. Agents 7 and 8 are independent and, crucially, are grounded in external databases — DDInter for interactions, RxClass for allergy classes — not just opinion. That is separation of duties, the same principle as a second doctor signing off.

14 · Saving state after every single step

Every time an agent finishes, its result is written to MongoDB immediately — not batched to the end.

The tiny helper that does it
async function updateStep(apptId: string, step: string, extra?: Record<string, unknown>) {
  await Appointment.findByIdAndUpdate(apptId, {
    agentPipelineStep: step,
    ...extra,                      // usually { agentOutputs }
  });
}

// Used like this, all through the pipeline:
await updateStep(appointmentId, "agent_6_running");
// …agent runs…
await updateStep(appointmentId, "agent_6_done", { agentOutputs });

Why save so often?

  • Live progress — the doctor's page polls the database, so each save instantly moves the progress bar.
  • Refresh-safe — completed agents stay completed. Only unfinished work restarts.
  • Crash-safe — if the server dies at agent 7, agents 2–6 results are already stored.
  • Debuggable — you can see exactly where a pipeline stopped.

The dot-notation rule (a bug that taught a lesson)

The bugThe pre-call route used to save with a whole-object write: { agentOutputs: {agent3, agent4, agent5} }. If the call had already ended and Agent 2 had written its result, this wiped Agent 2 — because replacing the object replaces everything in it. Agent 2 would mysteriously flip back to "Waiting" after a refresh.
The fix — write only specific keys
// ❌ WRONG — replaces the whole object, deleting siblings
await Appointment.findByIdAndUpdate(id, {
  agentOutputs: { agent3: ..., agent4: ..., agent5: ... }
});

// ✅ RIGHT — dot-notation touches ONLY these three fields
await Appointment.findByIdAndUpdate(id, {
  $set: {
    "agentOutputs.agent3": a3?.output ?? { ...fallback },
    "agentOutputs.agent4": a4?.output ?? { ...fallback },
    "agentOutputs.agent5": a5?.output ?? { ...fallback },
  },
});
Second rule: never store nullAn agent that legitimately found nothing (e.g. no similar cases) used to store null. The UI checked truthiness, so null looked identical to "never ran" and showed "Waiting" forever. Now a completed-but-empty agent stores a real object like { topCases: [], overallSummary: "No similar cases found." }, and the UI checks key presence ("agent3" in agentOutputs) rather than truthiness. "Ran and found nothing" and "hasn't run" must be distinguishable states.

15 · Error handling philosophy

The orchestrator treats different failures differently. That is a deliberate design, not an accident.

What failsWhat happensWhy
One of agents 3/4/5Others still save; a typed fallback object is stored for the failed onePartial context beats no context.
No audio capturedAgent 2 is skipped, marked { skipped: true, status: "no_audio" }Honesty — never invent a fake transcript.

The outer safety net (pipeline.ts)
try {
  // …the entire pipeline…
} catch (err) {
  console.error(`${tag} Pipeline FAILED:`, err);
  await updateStep(appointmentId, "pipeline_failed").catch(() => {});
  //                                                 ↑ even the error-write
  //                                                   can't throw
}
"Fail open" vs "fail closed" — know these termsFail closed = when unsure, block (a locked door that stays locked in a power cut). Fail open = when unsure, allow (a fire exit that unlocks in a power cut).

MediIQ fails open on verification tools (a dead LLM shouldn't stop the consultation) but fails closed on actual safety findings — a drug flagged by Agent 7 or 8 is always removed. That split is the correct medical-software choice, and a strong thing to articulate.

16 · How the doctor sees live progress

The orchestrator never pushes updates to the browser. Instead the browser polls — asks repeatedly.

1
Page loads → starts a 2.5-second poll loop

Each tick fetches the appointment and reads agentPipelineStep + agentOutputs.

2
First poll also triggers the pipeline — once

Guarded by a useRef flag in the browser and the atomic DB claim on the server. Two layers of protection.

3
Progress only moves forward

The UI compares the new step's position against the current one and refuses to go backwards — so an out-of-order response can't rewind the bar.

4
Outputs are merged, never replaced

setAgentOutputs(prev => ({ ...prev, ...data.agentOutputs })) — already-shown results can't disappear.

5
Stops at a terminal state

Polling ends on pipeline_done or pipeline_failed.

Why polling and not WebSockets?The app already has Socket.IO for the video call, so pushing would have been possible. Polling was chosen because it is stateless and serverless-friendly — the pipeline runs inside a serverless function that has no persistent socket to the browser. Polling the database works no matter which server instance handled the request. A 2.5s interval on a page open for ~1 minute is a trivial cost.

18 · How this compares to LangGraph

LangGraph is a Python/JS framework for building agent workflows as a graph: nodes (agents), edges (what runs next), conditional edges (branching), and cycles (loops). Here is an honest mapping.

LangGraph conceptIts MediIQ equivalent
NodeAn agent function matching AgentFn
EdgeThe order of await statements in pipeline.ts
Conditional edgeif (a7 PASS && a8 PASS) break;
CycleThe for (loop < MAX_LOOPS) block
Shared state objectThe agentOutputs object + the Appointment document
Checkpointer (persistence)updateStep() writing to MongoDB after every agent
Recursion limitMAX_LOOPS = 2
Parallel branchesPromise.allSettled([...])
Graph visualisationAGENT_REGISTRY + the admin "Full Pipeline Flow" page

What LangGraph would have given me

  • Built-in checkpointing and "resume from where it crashed".
  • Streaming of intermediate node outputs out of the box.
  • Graph visualisation for free.
  • A standard vocabulary other developers already know.
  • Human-in-the-loop interrupts as a first-class feature.

What building it myself gave me

  • Exact control of database writes — dot-notation updates were required to avoid clobbering sibling agent results. That's a MongoDB-specific concern a generic checkpointer wouldn't have handled the way I needed.
  • Serverless correctness — the awaited-route + atomic-claim design came from a platform constraint, not from the agent logic.
  • No extra dependency in an already large Next.js app.
  • Full understanding of every failure mode, because I wrote each one.
The balanced takeawayIf the graph were much bigger, more branching, or needed resume-after-crash, a framework would start winning. For a mostly-linear 9-agent flow with one bounded cycle, hand-writing it was the lighter, clearer choice — and it forced a real understanding of state, concurrency and idempotency. Being able to say both sides is what makes the answer strong.

20 · Honest limitations & what I'd improve

⏱️ No resume-after-crash

If the function dies mid-pipeline, the state field shows where it stopped, but there's no automatic "continue from agent 7". A LangGraph checkpointer or a job queue would give that.

🔁 No per-agent retry

A failed agent is recorded and skipped; there's no automatic retry with backoff for transient network errors.

📊 Polling isn't free

Every 2.5s the page hits the database. Fine at current scale; at thousands of concurrent consultations, server-sent events would be cheaper.

⛓️ Sequential phase 2

Agents 7 and 8 both only need Agent 6's output, so they could run in parallel. They currently run one after the other — an easy future speed-up.

🧭 Flow is hard-coded

The order lives in code. A config-driven or graph-defined flow would let non-developers change the pipeline.

⏳ maxDuration ceiling

A very slow model run could still hit the platform's function time limit. A background worker/queue would remove that ceiling entirely.

Saying these out loud is a strengthInterviewers rate candidates who can critique their own system. "Agents 7 and 8 could be parallel — I'd fix that next" shows you're still thinking about it, not just defending it.

21 · Interview Q&A

Q Did you use LangGraph or build it yourself? ›

I built it myself. lib/agents/pipeline.ts is a custom orchestrator in TypeScript — no LangGraph, no LangChain. It handles ordering, parallel fan-out, a bounded feedback loop, per-step persistence, and an atomic once-only claim. I evaluated LangGraph; it gives you graph state, cycles and checkpointing for free, but my flow was mostly linear with a single conditional cycle, and I needed precise control over MongoDB writes and Vercel's serverless timing — so a framework would have added weight without solving my actual hard problems.

Q Walk me through how the agents loop. ›

It's a bounded feedback cycle. Inside a for loop capped at 2 iterations: Agent 6 writes a prescription, then Agents 7 and 8 verify it against DDInter and RxClass. If both return PASS, I break. If either flags a drug, I collect every flag into an array and pass it into the next iteration as loopContext — so Agent 6 re-prescribes knowing exactly what to avoid. After 2 rounds, anything unresolved is escalated to the human doctor and the flagged drugs are filtered out of what's sent to the patient. The three essentials are feedback injection, an exit condition, and a hard bound.

Q How do you stop the pipeline running twice? ›

An atomic compare-and-swap in MongoDB. Before doing any work the route runs findOneAndUpdate with a filter on the current state and a $set to the next state. Only one caller can match the filter — everyone else gets null back and returns "already running". Because the read and write are one atomic operation, there's no race window like there would be with a read-then-write. The doctor's page polls every 2.5 seconds and can be open in multiple tabs, and it still runs exactly once.

Q How do you keep it fast? ›

Four ways. Pre-warming — agents 3/4/5 start when the patient locks their form, so they finish during the video call. Parallelism — those three run concurrently, so the cost is the slowest one, not the sum. Concurrent model race — the prescriber fires Gemini and the backup simultaneously rather than waiting for a timeout before falling back. Caching — each agent has its own cache collection with a sliding TTL, so a repeat consultation drops from ~70 external calls to about 3.

Q What happens if an agent fails? ›

It depends on which one, deliberately. The parallel agents use Promise.allSettled, so one failing never discards the others' completed work — each result is saved independently with a typed fallback for the failure. If there's no audio, Agent 2 is skipped and honestly marked "no audio detected" rather than inventing a transcript. If the verification LLM is unavailable, Agent 7 fails open and lets the doctor decide instead of blocking. And the entire pipeline is wrapped in a try/catch that sets pipeline_failed, so the UI shows an error rather than hanging.

Q How is state managed across steps? ›

A single field, agentPipelineStep, acts as a finite state machine, and each agent's output is written into agentOutputs the moment it finishes. Everything lives in MongoDB rather than memory, because serverless functions are stateless and short-lived. That makes the pipeline refresh-safe and crash-visible, drives the progress UI for free, and enables the atomic claim. I write with dot-notation $set so one agent's save can't clobber another's — I hit exactly that bug when a slow pre-warm agent overwrote Agent 2's result.

Q Biggest challenge building the orchestrator? ›

Running a long multi-step pipeline on serverless. On Vercel a function is frozen the instant it returns a response, so my original "respond immediately, run the agents in the background" design silently never executed — the page polled forever. I moved the pipeline into dedicated awaited routes with an extended maxDuration, added the atomic claim so constant polling couldn't spawn duplicates, and made every agent persist its result immediately so a refresh never loses progress. Debugging it taught me more about distributed state than the agent logic itself did.

Q Why not let one big AI do everything? ›

Separation of concerns. Small focused agents are individually testable, independently cacheable, and each can use the right tool — Agent 7 queries a drug-interaction database, Agent 3 does vector search, Agent 6 reasons. It's also a safety requirement: a model that checks its own prescription is biased toward approving it, so the checkers must be independent and grounded in external data. And when something goes wrong, I can see exactly which agent failed instead of debugging one giant opaque prompt.

Q How would you scale this to 50 agents? ›

At that size I'd stop hand-writing the flow. I'd move to a declarative graph definition — either LangGraph or my own config-driven runner using the existing AGENT_REGISTRY metadata, which already records consumes, produces and feedsInto for every agent. From that you can build the dependency graph automatically, topologically sort it, and run every independent layer in parallel without hard-coding the order. I'd also move execution to a durable job queue so long pipelines aren't bound by a serverless function's time limit, and add per-agent retries with backoff.
