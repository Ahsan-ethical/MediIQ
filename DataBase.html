1 · What this file covers

When a doctor treats a patient, they use knowledge from many places: their memory of past patients, medical textbooks, drug reference books, and allergy charts. MediIQ's AI needs the same things — but in digital form.

So the app pulls medical facts from 10 different data sources. Some we downloaded and stored inside our own MongoDB database. Others we call live over the internet while the patient is being treated.

The one-line summaryMediIQ mixes its own memory (past cases we have seen) with official free medical databases from the US government (NIH, FDA, National Library of Medicine) and a research drug-interaction dataset (DDInter). Nothing is invented by the AI — every medical fact traces back to a real source.

Why this matters so much

An AI language model on its own will sometimes make things up (this is called "hallucination"). In medicine that is dangerous. The fix is to give the AI real documents to read before it answers. Every database in this file exists to feed the AI real, checkable facts.

3 · The 3 types of data (very important to understand)

Before details, understand that our data falls into three buckets. Interviewers love this distinction because it shows you thought about speed vs freshness.

🏠 Type 1 — Data we own

Our own cases. Created by our app as doctors use it. Grows over time. Lives only in our database.

📦 Type 2 — Downloaded once

Bundled data. We downloaded big public datasets (MedlinePlus, FDA labels, DDInter, ICD-10) and loaded them into our database with seed scripts. Fast, works offline, never rate-limited.

🌐 Type 3 — Called live

Live APIs. Fetched from the internet during the consultation, because they change or are too big to download (RxNorm, RxClass, NIH, openFDA).

Why not download everything?

  • RxNorm/RxClass are enormous and change often — new medicines get added. Live is fresher.
  • DDInter is stable and huge (175k rows) — downloading it once makes checks instant, and there is no public API anyway.
  • MedlinePlus + FDA labels — we downloaded a curated slice so we could chop it up and embed it for AI search (you cannot do that against a live API).

Why not call everything live?

Because it would be slow and could fail. A consultation would need ~70 internet calls. Free government APIs also have rate limits. So we download what we can, and cache everything else (see section 10).

Our Own Databases

5 · Case Library — our own memory

Stored in our MongoDBCollection: cases131 documentsUsed by Agent 3

What is it?

Every time a consultation finishes, MediIQ saves an anonymised copy of it: the symptoms, what the doctor diagnosed, what medicines were given, and basic patient facts (age, sex, conditions). No names, no contact details.

Think of it as the clinic's collective memory. When a new patient arrives, the AI can ask: "Have we seen someone like this before? What worked?"

What one record actually looks like

This is a real (simplified) document from our database:

A real document in the "cases" collection
{
  "symptoms":  "Fever, leg pain",
  "duration":  "2 days",
  "severity":  "moderate",
  "patient": {
    "age": 21,  "sex": "Male",  "weight": 70,  "height": 175,
    "bloodGroup": "O+",
    "knownConditions": ["diabetes"],
    "allergies": [],
    "currentMedications": []
  },
  "diagnosis": "Acute Febrile Illness with Myalgia, likely viral...",
  "prescription": [
    { "medicine": "Paracetamol", "dosage": "500mg",
      "frequency": "as needed", "duration": "3 days" }
  ],
  "advice": "Rest, plenty of fluids, monitor blood glucose",
  "embedding": [0.013, -0.245, 0.087, ... ]   // 3072 numbers
}

The special part — the embedding field

Notice the last field. An embedding is a list of 3,072 numbers that represents the meaning of the case's symptoms. Two cases that mean similar things get similar numbers — even if they use totally different words.

Simple example"High temperature and body ache" and "Fever with myalgia" use different words but mean the same thing. Their embeddings will be very close together. This is how the computer finds similar cases without needing exact word matches.

How it is used during a consultation

1
Patient types symptoms

e.g. "Fever, body pain" in the pre-consultation form.

2
Agent 3 turns them into an embedding

Sends the text to Gemini, gets back 3,072 numbers.

3
MongoDB vector search

Compares that list against all 131 stored case embeddings and returns the closest ones.

4
Boost + re-rank

Cases with matching age/conditions get a small score boost, then the AI picks the best 10.

5
Handed to Agent 6

As "weak reference" context — helpful precedent, never to be copied blindly.

The actual vector search (from lib/agents/agent3.ts)
Case.aggregate([
  { $vectorSearch: {
      index:         "case_vector_index",
      path:          "embedding",
      queryVector:   embedding,   // patient's symptoms as 3072 numbers
      numCandidates: 150,         // scan 150 nearby cases
      limit:         50           // keep the best 50
  }},
  { $project: { embedding: 0 } }  // don't send the huge vector back
])
Interview question you WILL get"How do you stop the AI from just copying an old prescription?"
Answer: the prompt given to Agent 6 explicitly labels similar cases as "EPIDEMIOLOGICAL REFERENCES ONLY — do NOT copy their prescriptions", and instructs it to reason independently for this patient's age, allergies and comorbidities. Retrieval gives knowledge; the prompt enforces safety.

6 · Knowledge Library — the medical textbook

Stored in our MongoDBCollection: medicalcontexts3,347 chunksUsed by Agents 4, 5, 7

What is it?

This is MediIQ's digital textbook. We downloaded two big free medical sources, chopped them into small readable pieces ("chunks"), turned each piece into an embedding, and stored them so the AI can search them by meaning.

📘 MedlinePlus (2,424 chunks)

Plain-English articles about illnesses, written by the US National Library of Medicine. Tells you what a condition is, its symptoms, causes and treatment.

💊 openFDA drug labels (923 chunks)

Official FDA information printed on drug packaging: what it treats, the dose, who must not take it, warnings, and drug clashes.

How we built it (the "chunking" process)

You cannot embed a whole 5,000-word article — the meaning gets blurry. So the seed script splits things into small focused pieces:

1
MedlinePlus: split at question headings

Long articles are cut at natural headings like "What is…", "What causes…", "How is it treated…". Short articles stay as one chunk. Each chunk is capped at ~400 words.

2
openFDA: split by label section

Each drug becomes up to 6 chunks — one each for indication, dosage, contraindication, warning, boxed warning, interaction. This is why we can search "who must not take ibuprofen" precisely.

3
Add a header line before embedding

Each chunk's embed text starts with context, e.g. "Condition: Diabetes. Also known as: … Category: …" or "Drug: Ibuprofen. Contraindications: …". This makes the meaning much sharper.

4
Embed with Gemini + store

Every chunk gets its 3,072-number embedding and is inserted in batches of 50, with a small delay to respect API rate limits.

  "metadata": {

    "groups": ["Diagnostic Tests", "Diabetes Mellitus"],

How Agent 4 searches it — the clever part

Agent 4 does not run one search. It writes 5 different questions about the patient, and each question searches only the relevant type of chunk. This is called a filtered vector search.

#The question it asksOnly searches chunks of type
Q1"management of <symptoms>"condition
Q2"prescribing considerations and drugs to avoid in <conditions>"contraindication, warning
Q3"treating <symptom> in patients with <condition>"condition
Q4"drug interactions and contraindications for <symptoms> meds"interaction, contraindication
Q5"warning signs and referral criteria for <symptoms>"warning, condition

Quality controls applied to the results

  • Score floor (0.80): anything less similar than 0.80 is thrown away — no weak matches.
  • Combo-drug penalty: products with 2+ commas in the name (e.g. "Paracetamol, Caffeine, Phenylephrine") lose 0.04 score — single-ingredient info is more useful.
  • Duplicate removal: identical text (by MD5 hash) is kept only once, at its best score.
  • Source balancing: keeps at least 5 MedlinePlus chunks so drug labels don't drown out condition knowledge. Final answer = 15 chunks max.
Why this design is goodFiltering by type means when we ask about "drugs to avoid", we only search the contraindication/warning chunks — so we never get a cheerful "what is diabetes" article back when we asked a safety question. That is far more accurate than one big unfiltered search.

7 · ICD-10 Lookup Table

Stored in our MongoDBCollection: ConditionLookUp2,134 rowsUsed by Agent 4

What is ICD-10?

ICD-10 is the world's official code list for diseases, run by the WHO. Every illness has a short code. For example, a cut/laceration is T14.8XXA.

Why codes instead of words? Because people write the same illness in many ways — "sugar", "diabetes", "diabetes mellitus", "DM type 2". A code removes all confusion, and other medical services (like MedlinePlus) accept codes to give you the exact right article.

What a row looks like

Real row from ConditionLookUp
{
  "condition":      "laceration",
  "condition_norm": "laceration",     // cleaned version used for matching
  "code":           "T14.8XXA"        // the official ICD-10 code
}

The "normalize" trick

Before looking anything up, the text is normalised: lowercased, punctuation removed, extra spaces squashed, and the words sorted alphabetically.

Why sorting words matters
"Type 2 Diabetes"     → "2 diabetes type"
"Diabetes, Type 2"    → "2 diabetes type"     ← same key!
"diabetes type 2"     → "2 diabetes type"     ← same key!

All three spellings become the same lookup key, so they all find the same code. Simple but very effective.

The 2-step lookup (local first, internet second)

1
Check our own table

Instant — no internet needed. Covers 2,134 common conditions.

2
Not found? Ask NIH live

Calls the NIH Clinical Tables API (section 11).

3
Save the answer back

The new code is written into our table, so next time it is instant. The table learns and grows.

Nice detail to mentionThis is called a "cache-back" or self-populating lookup. It started smaller and has grown to 2,134 entries as real patients used the app.

8 · DDInter — the drug clash database

Stored in our MongoDBCollection: DrugInteractions175,201 rowsUsed by Agent 7

What is DDInter?

DDInter is a free research database of drug-drug interactions — meaning: "if a patient takes drug A and drug B together, is that dangerous?" Each pair is graded Major, Moderate, or Minor.

Why this is life-or-deathSome medicines are perfectly safe alone but harmful together. Example: certain antibiotics + certain heart medicines can cause dangerous heart-rhythm problems. A busy doctor cannot memorise 175,000 combinations — the computer can check them all in milliseconds.

How we loaded it

We downloaded 8 CSV files from DDInter (split by drug category: A, B, D, H, L, P, R, V — these are ATC groups like Alimentary, Blood, Dermatological, etc.). The seed script:

  1. Reads all 8 CSVs (~222,000 raw rows).
  2. Skips broken rows and any level that isn't Major/Moderate/Minor.
  3. Normalises both drug names (lowercase, remove bracketed notes like "(topical)").
  4. Inserts in batches of 5,000 → 175,201 clean rows.
  5. Creates two indexes so lookups are instant in both directions.

What a row looks like

Real row from DrugInteractions
{
  "drug_a":      "Metformin",
  "drug_b":      "Abemaciclib",
  "drug_a_norm": "metformin",      // normalised for fast matching
  "drug_b_norm": "abemaciclib",
  "level":       "Moderate",       // Major | Moderate | Minor
  "ddi_id_a":    "DDInter1164",
  "ddi_id_b":    "DDInter7"
}

The two-index trick (great interview point)

The database stores the pair as "Metformin + Abemaciclib". But a doctor might prescribe them in the other order. So we build two indexes:

Both directions indexed
createIndex({ drug_a_norm: 1, drug_b_norm: 1 })   // idx_pair_ab
createIndex({ drug_b_norm: 1, drug_a_norm: 1 })   // idx_pair_ba

// And the query checks both directions at once:
col.findOne({ $or: [
  { drug_a_norm: "metformin",   drug_b_norm: "azithromycin" },
  { drug_a_norm: "azithromycin", drug_b_norm: "metformin"   }
]})

Without this, a valid dangerous pair could be missed just because of the order the doctor typed them. An index makes each lookup take about a millisecond instead of scanning 175,201 rows.

How Agent 7 uses it

Agent 7 takes every prescribed medicine + every medicine the patient already takes and builds all possible pairs.

Example: 2 new drugs + 2 existing drugs = 6 pairs to check
Prescribed: Azithromycin, Paracetamol
Already taking: Metformin, Amlodipine

Pairs checked:
  1. Azithromycin ↔ Paracetamol
  2. Azithromycin ↔ Metformin
  3. Azithromycin ↔ Amlodipine
  4. Paracetamol  ↔ Metformin
  5. Paracetamol  ↔ Amlodipine
  6. Metformin    ↔ Amlodipine

Any pair that comes back "Major" → that drug is FLAGGED
→ sent back to Agent 6 to pick a safer alternative.

All pairs are checked in parallel, and every result (including "no interaction found") is cached so repeat consultations are nearly free.

10 · Cache collections — how we avoid repeating work

A cache is a saved answer. If we already asked a question once, we store the answer and reuse it instead of asking again. This is the single biggest speed win in the whole app.

Cache collectionWhat it remembersSaves us from
agent3similarcasescachesWhole similar-case results for a symptom set.Re-running embedding + vector search + 2 LLM calls.
agent4_medical_context_cache4 things: full output, MedlinePlus summaries, retrieval queries, query embeddings.NIH + MedlinePlus calls, 5 embeddings, 2 LLM calls.
agent5_allergy_context_cacheFull output + per-allergen expansions + embeddings.RxClass API calls.
agent7_drug_medic_cacheFDA labels, library context, and every drug-pair verdict.openFDA calls + DDInter lookups.
agent8_allergy_check_cacheRxCUI lookups + drug-class member lists.RxNorm + RxClass calls.

"Sliding TTL" explained simply

TTL = Time To Live = how long a saved answer stays valid. Ours is 140 days. "Sliding" means every time the answer gets used, its clock resets to another 140 days.

The effectPopular answers (common illnesses, common drugs) never expire because they keep getting used. Rare, one-off answers quietly delete themselves after 140 days. MongoDB removes them automatically using a TTL index on expiresAt — we don't run any cleanup job.

One exception: drug-name → RxCUI lookups are cached for 10 years, because a medicine's official ID number never changes.

The measurable result

ScenarioExternal calls needed
First-ever consultation for a symptom set (cold cache)~70+
A repeat/similar consultation (warm cache)~3 (LLM only)

The remaining ~3 are the AI reasoning calls, which must run fresh because the patient is different every time.

Live Medical APIs

11 · NIH Clinical Tables — name → ICD-10 code

Live internet APIclinicaltables.nlm.nih.govFree, no key neededUsed by Agent 4

What is it?

A free service from the US National Library of Medicine. You give it an illness name, it gives you the official ICD-10 code. We only call it when our own lookup table (§7) does not already know the answer.

The real call

Request (from lib/agents/condition-resolver.ts)
GET https://clinicaltables.nlm.nih.gov/api/conditions/v3/search
      ?terms=diabetes
      &ef=icd10cm

Timeout: 8 seconds
Response shape (an array of 4 things)
[
  7,                                       // [0] how many matches
  ["id1","id2", ...],                      // [1] internal ids
  { "icd10cm": [[{ "code":"E11.9",         // [2] the codes
                   "name":"Type 2 diabetes mellitus..." }]] },
  [["Diabetes"]]                           // [3] display names
]

The safety gate (important detail)

APIs can return a confidently wrong match. So before trusting the code, we do a token overlap check: at least one word from what the patient wrote must also appear in the matched disease name.

Why the gate exists
Patient wrote:  "sneeze"
API returned:   "Bacterial infection, unspecified"
Shared words:   0   →  REJECTED, code marked "unresolved"

Patient wrote:  "diabetes"
API returned:   "Type 2 diabetes mellitus"
Shared words:   1 ("diabetes")  →  ACCEPTED

If accepted, the code is written back into our own lookup table so we never need to ask again.

Three possible outcomesEvery condition ends up labelled with a codeSource: lookup (found locally, instant), nih_api (fetched live), or unresolved (nobody could match it — the app continues honestly without a code).

12 · MedlinePlus Connect — code → patient-friendly article

Live internet APIconnect.medlineplus.govFree, no keyUsed by Agent 4

What is it?

Give it an ICD-10 code, and it returns an official, easy-to-read explanation of that condition, written for ordinary people. This is how MediIQ turns a cold code like E11.9 into a real explanation the AI (and the doctor) can use.

The real call

Request (from lib/agents/condition-resolver.ts)
GET https://connect.medlineplus.gov/service
      ?mainSearchCriteria.v.cs=2.16.840.1.113883.6.90   // "this is an ICD-10 code"
      &mainSearchCriteria.v.c=E11.9                      // the code itself
      &knowledgeResponseType=application/json
      &informationRecipient.languageCode.c=en            // English

Timeout: 10 seconds

That long number 2.16.840.1.113883.6.90 is just the official ID meaning "the code I'm sending is ICD-10-CM". It never changes.

Response (simplified)
{ "feed": { "entry": [ {
      "title":   { "_value": "Diabetes Type 2" },
      "link":    [{ "href": "https://medlineplus.gov/diabetestype2.html" }],
      "summary": { "_value": "<p>Type 2 diabetes is a disease in which
                              your blood glucose levels are too high...</p>" }
} ] } }

What we do with the answer

1
Strip the HTML tags

The summary comes with <p> tags — we remove them so it is clean text.

2
Condense it with the LLM

The AI rewrites it into a fixed clinical shape: Overview → Key symptoms → Common causes → Major complications → Treatment essentials. The prompt says "do NOT add anything not in the source".

3
Cache the result for 140 days

Keyed by the ICD-10 code, so the next diabetic patient gets it instantly with zero calls.

Two caches protect this one APIThere is a 12-hour in-memory cache inside the app process, plus the 140-day MongoDB cache. The same condition is essentially never fetched twice.

13 · MedlinePlus Web Search — wording hints

Live internet APIwsearch.nlm.nih.govFree, no keyUsed by Agent 4

What is it, and why is it different?

This one searches MedlinePlus health topics by free text. MediIQ uses it in a small but smart way: not for medical facts, but for correct medical wording.

Before Agent 4 writes its 5 search questions, it asks this API "what are the official topic names related to these symptoms?" and gets back up to 3 titles. Those titles are given to the AI as "wording inspiration only", so the questions it writes use proper medical vocabulary instead of casual patient language.

Request + what we extract
GET https://wsearch.nlm.nih.gov/ws/query
      ?db=healthTopics
      &term=fever%20body%20pain
      &retmax=3

Response is XML. We pull out up to 3 of these:
  <content name="title">Fever</content>
  <content name="title">Muscle Disorders</content>

Timeout: 6 seconds — and if it fails, we simply carry on with none.
Graceful failureThis call is completely optional. If it times out or errors, the function returns an empty list and the pipeline continues normally. Nothing breaks — a good example of designing around unreliable third-party services.

14 · RxNorm — the official medicine dictionary

Live internet APIrxnav.nlm.nih.gov/RESTFree, no keyUsed by Agents 2 & 8

What is it?

RxNorm is the US National Library of Medicine's official dictionary of medicines. Every medicine has a unique ID number called an RxCUI.

The problem it solvesThe same medicine has many names: Paracetamol (UK/India), Acetaminophen (US), Tylenol (brand), Crocin (brand), plus typos like "paracetmol". To a computer these are 5 different strings. RxNorm maps them all to one RxCUI number — so we can compare medicines reliably.

Two-step lookup with typo tolerance

Step 1 — exact name search (from lib/agents/agent2.ts)
GET https://rxnav.nlm.nih.gov/REST/rxcui.json?name=Paracetamol&search=2

→ { "idGroup": { "rxnormId": ["161"] } }

Then fetch the official name:
GET https://rxnav.nlm.nih.gov/REST/rxcui/161/properties.json
→ { "properties": { "rxcui": "161", "name": "acetaminophen" } }
Step 2 — approximate match (only if step 1 fails)
GET https://rxnav.nlm.nih.gov/REST/approximateTerm.json
      ?term=paracetmol      ← misspelled!
      &maxEntries=1

→ { "approximateGroup": { "candidate": [
      { "rxcui": "161", "name": "acetaminophen" } ] } }

This is what makes the system forgiving of doctor/patient typos.

Where it is used

Agent 2 — after the call

Takes every medicine name mentioned in the conversation, strips the dose ("500 mg" removed), and looks up the real name + RxCUI. Any drug it cannot match is honestly marked unrecognized and the agent returns a "flag" status.

Agent 8 — allergy checking

Converts each prescribed drug into its RxCUI so it can be compared against the RxCUI list of the patient's allergy drug-class (see §15).

All lookups run in parallel and are cached essentially forever (10 years), because a medicine's ID number never changes. Even "not found" results are cached, so we don't retry a bad name repeatedly.

15 · RxClass — drug families for allergy safety

Live internet APIrxnav.nlm.nih.gov/REST/rxclassFree, no keyUsed by Agents 5 & 8

What is it, and why is it critical?

RxClass tells you which family a medicine belongs to. This is the single most important idea in MediIQ's allergy safety.

The danger it preventsA patient says "I am allergic to Penicillin." A naive system would only block the exact word "Penicillin" — and would happily prescribe Amoxicillin, which is also a penicillin and could cause a life-threatening reaction. RxClass expands one allergy into the whole drug family, so all of them get blocked.

Step 1 — allergen → drug class

First, a small built-in map converts an allergy word into a real example drug (because RxClass needs a drug, not a class name):

The allergen → example drug map (agent5.ts)
penicillin      → amoxicillin        nsaid / nsaids  → ibuprofen
sulfonamide     → sulfamethoxazole   tetracycline    → doxycycline
sulfa           → sulfamethoxazole   fluoroquinolone → ciprofloxacin
cephalosporin   → cephalexin         macrolide       → azithromycin
aspirin         → aspirin            statin          → atorvastatin
Then ask RxClass for the class
GET https://rxnav.nlm.nih.gov/REST/rxclass/class/byDrugName.json
      ?drugName=amoxicillin
      &relaSource=ATC

→ rxclassDrugInfoList.rxclassDrugInfo[].rxclassMinConceptItem
   { "className": "BETA-LACTAM ANTIBACTERIALS, PENICILLINS",
     "classId":   "J01C" }

ATC means "Anatomical Therapeutic Chemical" — the WHO's official way of grouping drugs. We prefer a class whose id looks like J01C (letter-digit-digit-letter) and skip "combination" classes, because those are the clean, standard groupings.

Step 2 — class → all its member drugs

Get everyone in the family
GET https://rxnav.nlm.nih.gov/REST/rxclass/classMembers.json
      ?classId=J01C
      &relaSource=ATC

→ Amoxicillin, Ampicillin, Penicillin G, Penicillin V, Piperacillin,
  Flucloxacillin, ... (we keep up to 30 names)

This entire list becomes the patient's "avoid drugs" list.

Some allergies are risky across families. This knowledge is hard-coded because it is stable, well-established medicine:

Step 4 — how strongly to block it

Agent 5 combines how sure we are with how bad the reaction is:

Status + SeverityAvoid levelMeaning

confirmed + mildstrong_cautionAvoid unless clearly necessary.
suspected + severelikely_blockTreat as blocked until confirmed.
anything elsemonitorAllowed, but watch the patient.

How Agent 8 uses all this (three checks)

1
Name check (instant, no internet)

Is the prescribed drug's name in the avoid list? Most hits are caught here for free.

2
RxCUI class check

Only for drugs that passed check 1: convert the drug to its RxCUI and see if that ID is in the allergy class's member ID list. This catches brand names and spellings the name check missed.

3
Cross-reactivity check

Finally compare against the cross-reactivity families above.

Smart efficiencyNotice the order: the free check runs first, and the paid/slow internet check runs only for drugs that survived it. If a drug is already blocked by name, we never waste an API call on it.

16 · openFDA — official drug labels

Live internet APIapi.fda.govFree, no keyUsed by Agent 7
…and also stored offline923 chunks inside medicalcontexts

What is it?

openFDA is the US Food & Drug Administration's official open database. The drug label endpoint gives you exactly what is printed on the official packaging insert: what the drug treats, correct doses, who must not take it, and its warnings.

The real call

Request (from lib/agents/agent7.ts)
GET https://api.fda.gov/drug/label.json
      ?search=openfda.generic_name:"paracetamol"
      &limit=1

Timeout: 8 seconds

We only read two fields from the big response:
  • indications_and_usage      → what it is approved to treat
  • dosage_and_administration  → the approved dose range
Each is trimmed to 500 characters to keep the AI prompt small.

Why openFDA appears TWICE in this project

This confuses people, so it is worth being clear — we use FDA data in two different ways:

🌐 Live API (Agent 7)

Fetches the full label for a specific named drug we are about to prescribe. Exact lookup by drug name. Cached in MongoDB.

📦 Offline chunks (Agents 4, 5, 7)

923 pre-embedded label chunks inside our knowledge library, searched by meaning. Used when we don't know which drug to look up yet — e.g. "what should diabetics avoid?"

In one lineThe live API answers "tell me about THIS drug". The offline chunks answer "find me anything relevant to THIS situation". Different questions, so both are needed.

How Agent 7 verifies a prescription with it

1
Fetch label + library context for every drug — in parallel

Both are cached, so this is usually instant.

2
Build ONE combined prompt for all drugs

Each drug's FDA indications, FDA dosing, and library notes are stacked into a single block.

3
One LLM call answers for all drugs

For each: does the diagnosis match its approved use (MATCH/NOMATCH) and is the dose in range (PASS/FAIL)?

4
Combine with the DDInter result

Any drug in a Major interaction is also flagged. Flags go back to Agent 6.

Efficiency detail worth quotingAgent 7 checks all medicines in a single LLM call instead of one call per medicine. For a 4-drug prescription that is 1 call instead of 4 — roughly 4× faster and 4× cheaper. If the LLM is unavailable, it fails open (treats drugs as acceptable) and lets the human doctor decide, rather than blocking the whole pipeline.

19 · Embeddings & vector search explained simply

What is an embedding?

An embedding is a list of numbers that captures the meaning of a piece of text. MediIQ uses Google's gemini-embedding-001, which produces 3,072 numbers for any text.

Easy way to picture itImagine every sentence is a dot on a giant map. Sentences about fever land in one area; sentences about broken bones land far away. The 3,072 numbers are just the coordinates of that dot. "Finding similar cases" = "finding the nearest dots".

Where embeddings are used

CollectionVector index nameWhat is embedded
casescase_vector_indexSymptoms + duration + severity + notes of a past case
medicalcontextsmedicalcontext_vector_indexEach knowledge chunk, with a context header prepended

Why only symptoms are embedded for case search

When building the search text for Agent 3, MediIQ deliberately includes only symptoms, duration, severity and notes — not age or conditions.

Why? Because we want matching by illness, not by person. If demographics were embedded, a 45-year-old with a broken leg might match a 45-year-old with a fever, just because both are 45. Instead demographics are applied afterwards as a scoring boost — the best of both worlds.

The one permanent rule about embeddings

Embeddings are ALWAYS GeminiEven when the admin switches the AI engine to DeepSeek or Ollama, embeddings still use Gemini. Reason: the stored vectors were created by Gemini. A different model produces a different "map", so a DeepSeek query vector would be meaningless against Gemini-built vectors — search would return nonsense. Query and stored vectors must always come from the same model.

This is also why Agent 4's badge can read "deepseek + medlineplus + vector" — the reasoning ran on DeepSeek while the embedding ran on Gemini.

20 · Why these sources were chosen

ChoiceReason
Official government sources (NIH, FDA, NLM)Free, trustworthy, and citable. Random web text would be unsafe for medical use.
No API keys neededAll medical APIs used are open. No cost, no vendor lock-in, easy to reproduce.
DDInter downloaded, not called liveThere is no public API, the data is stable, and 175k local rows with indexes are far faster than any network call.
MedlinePlus/FDA chunked locallyYou cannot vector-search a live API. To search by meaning we must own and embed the text.
RxNorm/RxClass called liveThey are huge and updated as new drugs appear — live keeps us current, and caching removes the speed cost.
Everything cached 140 daysMedical facts change slowly. Caching cuts ~70 external calls to ~3 without hurting accuracy.
Two safety databases, not oneDDInter answers "do these drugs clash?"; RxClass answers "will this trigger the allergy?". Different risks need different sources.

Honest limitations (say these before being asked)

  • Case library is small (131 cases) — RAG quality improves as it grows.
  • US-centric data. FDA labels and MedlinePlus are American; Indian brand names may not resolve in RxNorm.
  • Cross-reactivity is hard-coded for the main families rather than fully data-driven.
  • Cached facts could go stale within the 140-day window if a drug warning changes.
  • Not a certified medical device — a licensed doctor signs every prescription.

21 · Interview Q&A — data layer

Q Which databases does your project use? ›

One MongoDB Atlas database with two roles. Operational collections (users, appointments, profiles) and medical knowledge stores: a 131-case library with 3072-dim embeddings, a 3,347-chunk knowledge library built from MedlinePlus + openFDA, a 2,134-row ICD-10 lookup, and 175,201 DDInter drug-interaction pairs. On top of that we call six free medical APIs live: NIH Clinical Tables, MedlinePlus Connect, MedlinePlus wsearch, RxNorm, RxClass and openFDA.

Q Why store some data locally and call other data live? ›

Three factors: speed, searchability, and freshness. DDInter has no API and is stable, so 175k indexed local rows give millisecond lookups. MedlinePlus/FDA text had to be local because you cannot run vector search against a remote API — we needed to chunk and embed it ourselves. RxNorm/RxClass change as new drugs launch, so they stay live, and heavy caching removes the latency penalty.

Q How does a penicillin allergy block amoxicillin? ›

Name matching alone would fail, because "amoxicillin" doesn't contain the word "penicillin". So Agent 5 maps the allergen to an example drug (amoxicillin), asks RxClass for its ATC class (J01C — beta-lactam penicillins), and pulls every member of that class into an avoid list. Agent 8 then checks each prescribed drug three ways: by name, by RxCUI against the class member IDs, and against hard-coded cross-reactivity families. Amoxicillin is caught on the very first check.

Q How do you keep it fast with so many sources? ›

Four techniques. (1) Pre-computation — allergy classes are resolved when the profile is saved, not during the consultation. (2) Parallelism — Agents 3/4/5 run together, drug pairs and API fetches run together. (3) Multi-level caching — 5 cache collections with 140-day sliding TTL, taking a repeat consultation from ~70 external calls to ~3. (4) Batching — Agent 7 verifies all drugs in a single LLM call instead of one per drug.

Q What is a sliding TTL and why use it? ›

TTL is how long a cached answer lives — ours is 140 days. "Sliding" means each use resets the clock. The effect is that frequently-needed facts (common illnesses, common drugs) effectively never expire, while rare one-off entries clean themselves up. MongoDB deletes them automatically via a TTL index on expiresAt, so there's no cleanup job to maintain.

Q How do you stop the AI hallucinating medical facts? ›

Retrieval plus constraints. Every fact is retrieved from a real source before the AI writes anything, and the summarising prompt says explicitly "do NOT add information not found in the chunks" and "preserve every caution verbatim". Retrieved chunks must clear a 0.80 similarity floor. Then two independent safety agents check the output against DDInter and RxClass, and finally a licensed doctor reviews and signs.

Q Why does vector search need 3072 numbers? ›

That's the output size of gemini-embedding-001. More dimensions capture finer shades of meaning. The important constraint is consistency: the Atlas index is configured for 3072 dimensions, and query vectors must come from the same model — which is why embeddings always use Gemini even when the reasoning model is switched to DeepSeek or Ollama.

Q What happens if an external API is down? ›

Every external call has a timeout (6–10s) and is wrapped so failure is non-fatal. wsearch returns an empty hint list; ICD-10 falls back to "unresolved"; a missing FDA label becomes "Not available" in the prompt; if the verification LLM fails, Agent 7 fails open and lets the doctor decide. Negative results are cached too, so we don't hammer a failing service. The pipeline always finishes with whatever real data it could gather — it never blocks and never invents a substitute.
